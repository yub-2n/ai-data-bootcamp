# v7 코드 시험 기록 (Chronos 결과 없이 할 수 있는 검증)

v7 코드는 v6 코드에서 원점 목록·파일 이름·평가 집합 규칙·속도만 바꾼 것이다. 이 환경에는 GPU와 Chronos-2 모델 접근이 없어 v7의 Chronos 결과는 아직 없다. 그래서 아래 두 가지로 코드를 먼저 시험했다.

## 1. v6 회귀 시험: 새 코드가 v6 숫자를 그대로 재현하는가
`ORIGINS_SET=v6`(원점 26개 + 명절 4개)로 v7 코드를 돌리고, 입력으로 v6의 Chronos 결과를 썼다.
- `12_export_eval_rows_v7.py`로 평가 표를 처음부터 다시 만든 결과가 v6의 `eval_rows_v6.parquet`와 같다(58,296행, 키 열 동일, actual·q50·q80 최대 차이 0).
- 최종FVA표(부트스트랩 구간 포함), A vs B, 메인주제표, 절감액 분해, 2026-01-01 권고표(md·long csv), 시드 확인, 자주 하는 실수 측정, 원인 확인, 작업 1·2, 가이드 요구사항 표 모음, 7행 민감도, 가정 바꾸기 백테스트가 v6 결과 파일과 숫자가 같다(제목과 버전 표기, 7행 민감도의 일부 설명 문장만 v7용으로 바꿨다).
- `19_alt_service_levels_backtest.py`는 개소 비중 계산을 캐시해 62초에 끝난다(v6 코드로는 이 환경에서 8분 이상 걸려도 끝나지 않았다). 결과는 v6와 같다.

## 2. Colab 스크립트 구동 시험(시험용 예측 사용)
`05b_run_chronos_colab_v7.py --stub`(모델 없이 직전 7일 평균 기반의 가짜 분위수를 쓰는 시험 모드)로 82개 원점 전체를 돌렸다.
- 행 수 25,830 = 82 × 5행 × 9계열 × 7일. 정기 원점 78개 검증, 행사 파일 해시 가드, 미래 정보 누수 검사(assert)를 통과했다.
- 이 시험 결과로 후속 스크립트(12, 최종FVA표, 24, 23, 28, 29, 14, 17, 18, 16, 21, 작업1~3, 27, 22, 30, 31, 19)를 모두 실행했고 오류가 없었다. 평가 개소·일 수가 FVA 7개 행에서 같다(A 격자 10,644, B 격자 10,636, 명절 575).
- 시험용 예측의 숫자는 의미가 없어 어떤 결과 파일에도 포함하지 않았다. 이 시험은 코드 경로 검증용이다.

## 3. 시험에서 확인된 실제 사실 (Chronos와 무관한 값)
- v6와 v7이 공유하는 30개 원점의 FVA 1·2행(직전 7일 평균, 서비스수준 보정)은 v6와 값이 완전히 같다(A·B 각 4,164행, 달라진 행 0).
- 직전 7일 평균이 없는 개소·원점은 A 2건(10개소·일), B 3건(18개소·일)이고 모든 FVA 행에서 같이 제외한다.

## 4. 아직 하지 못한 것
실제 Chronos-2 출력으로 FVA 3~7행, 권고표, 재현성(두 번 실행) 결과를 만드는 일. Colab 실행 후 `README_실행순서_v7.md`의 순서대로 진행한다.

## 5. 실제 Chronos 결과를 넣은 뒤의 확인
- Colab 결과 4개 파일: A·B 각 25,830행(82원점 × 5행 × 63), 분위수 단조 위반 0, NaN 0, 권고표용 63행. 재현성 최대 차이 0.
- `12_export_eval_rows_v7.py` → 157,010행, FVA 7개 행의 평가 개소·일 수 동일(A 정기 10,644 / B 정기 10,636 / 명절 575). `검증하기_v7.py` 모두 일치.
- v6와 겹치는 30개 원점의 FVA 1~7행 58,296행이 v6와 같다(달라진 행 0). 행사 파일 변경이 모델 공변량을 바꾸는지 따로 확인한 결과, 9개 계열 × 확정 시점 245일 × 전체 날짜 × 공변량 8개의 최대 차이가 0이었다(05b의 휴관 예상일 처리 때문). 이 진단에서만 이전 행사 파일을 읽기 전용으로 비교에 썼고 v7 결과에는 쓰지 않았다.
- 시험용(stub) 예측으로 확인한 `32_strict_notice_sensitivity_v7.py`는 실제 엄격 기준 결과가 오면 처음 실행하는 스크립트다.
